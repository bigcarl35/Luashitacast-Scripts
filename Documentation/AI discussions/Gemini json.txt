2. The Lua Configuration Loader

Using Ashita's native ashita.fs (file system) and json libraries, you can build a centralized loader function. It reads the string block from the hard drive, instantly decodes it into a
standard, fast Lua memory table, and binds it to your global configurations:

    -- Centralized Configuration Manager
    local json = require('json');

    function utilities.LoadDisplaySettings()
        -- Define the file path within your addon or profile subfolders
        local filePath = string.format('%ssettings/display_settings.json', ashita.addon.path);

        -- 1. Verify if the file physically exists on the disk
        if not ashita.fs.exists(filePath) then
            print("Display settings file not found! Loading engine defaults.");
            utilities.LoadDefaultDisplaySettings();
            return;
        end

        -- 2. Read the raw text block from the file
        local fileContent = ashita.fs.read_file(filePath);
        if not fileContent or fileContent == "" then
            print("Display settings file is empty!");
            return;
        end

        -- 3. Decode the raw JSON string instantly into your global LUA table
        local decodedData, pos, err = json.decode(fileContent);

        if err then
            print("Error parsing JSON display configurations: " .. tostring(err));
            return;
        end

        -- Success: Map the configuration directly to your active framework register
        gVars.DisplaySettings = decodedData;
        print("UI Display Configurations successfully loaded from JSON cache!");

        -- Optional: Trigger a UI redraw event to apply the freshly loaded values
        utilities.RefreshUIElements();
    end

3. Hooking into Job Swaps & LuAshitacast Load

To make sure this executes perfectly right as your state transitions occur, you hook the loading execution into your setup lifecycle blocks:

- At Initialization (LuAshitacast Load): Call utilities.LoadDisplaySettings(); inside your main framework's initialization file (addon:load event or main inclusion header).

- At Job Changes: Inside the entry point wrapper of your profile handler (such as the primary function that switches sets when gData.GetPlayer().MainJob changes), place a call
  to refresh or selectively merge configurations if you have job-specific UI sub-elements.

Why this upgrade is incredibly efficient:

- Zero Disk Thrashing: Reading the file happens exactly once during a transitional event (loading or switching characters/jobs). The rest of the time, your UI display rendering
  engine reads from gVars.DisplaySettings inside Lua memory at a 0-cost threshold.

- Safer File Formats: JSON is strictly parsed. If you accidentally misplace a bracket or make a layout error while modifying your settings, Ashita's JSON decoder catches the
  syntax exception gracefully (if err then), preventing your active Lua environment from crashing your game client or disabling your gear swaps mid-fight.

        utilities.RebuildScreenElements();

            local isActive = gVars.Toggles[toggleName];

            -- Determine the color dynamically based on state without magic coding arrays
            local drawColor = isActive and toggleData.ActiveColor or toggleData.InactiveColor;

1. Converting JSON Color Formats for ImGui

In standard text objects, colors are often written as full hex strings (like 0xFF00FF00). However, ImGui expects color vectors (either broken down into separate float
values from 0.0 to 1.0 or handled directly via custom ABGR integer conversions).

Since you are writing your configuration files in JSON, storing colors as standard HTML-style hex color strings (e.g., #00FF00 for green) makes the file highly readable.
You can implement a fast parsing function at load time to convert those hex strings into ready-to-use ImGui colors:

    -- Helper to convert string hex codes into ImGui-digestible vectors
    function utilities.HexToImGuiColor(hexStr)
        -- Expects format "#RRGGBB"
        local hex = hexStr:gsub("#", "")
        local r = tonumber("0x" .. hex:sub(1, 2)) / 255
        local g = tonumber("0x" .. hex:sub(3, 4)) / 255
        local b = tonumber("0x" .. hex:sub(5, 6)) / 255
        return { r, g, b, 1.0 } -- Returns an RGBA array matching ImGui specs
    end

Your JSON file configuration block can then look remarkably clean:

    "Toggles": {
        "ChainAffinity": { "Label": "CA", "ActiveColor": "#00FFCC", "InactiveColor": "#555555" },
        "BurstAffinity": { "Label": "BA", "ActiveColor": "#FFAA00", "InactiveColor": "#555555" }
    }

2. The Unified ImGui Rendering Loop

By registering an event handler via Ashita v4's d3d_present render pass, your UI code can scale dynamically without any hardcoded asset injections. It uses ImGui layouts
to space elements cleanly across the container width:

    local imgui = require('imgui');

    ashita.events.register('d3d_present', 'framework_imgui_renderer', function ()
        local layout = gVars.ActiveUI.Layout;
        local profile = gVars.ActiveUI.Profile;

        -- Safety Check: If JSON hasn't finished parsing or if the UI is hidden, skip execution
        if not layout or not profile or not layout.Visible then return end

        -- 1. Setup the basic window positioning constraints from your JSON file
        imgui.set_next_window_pos({ layout.PositionX, layout.PositionY }, imgui.cond_first_use_ever);
        imgui.set_next_window_size({ layout.Width, layout.Height }, imgui.cond_always);

        -- 2. Open the foundational status container window
        local windowFlags = bit.bor(imgui.window_flags_no_title_bar, imgui.window_flags_no_resize, imgui.window_flags_no_scroll_bar);

        if imgui.begin("Framework_Status_Bar", true, windowFlags) then

            -- Draw common cross-job strings (like TP text, target HP%, etc.)
            imgui.text("TP: " .. tostring(gData.GetPlayer().TP));

            -- Move to the exact same rendering line for subsequent toggles
            imgui.same_line();
            imgui.separator();
            imgui.same_line();

            -- 3. DYNAMIC INJECTION: Loop through the current job profile's active toggles
            if profile.Toggles then
                for toggleName, toggleData in pairs(profile.Toggles) do

                    -- Check your runtime jump-table flags to see if the toggle is active
                    local isActive = gVars.Toggles[toggleName];

                    -- Dynamic Color Selection from our JSON file properties
                    local rawHexColor = isActive and toggleData.ActiveColor or toggleData.InactiveColor;
                    local displayColor = utilities.HexToImGuiColor(rawHexColor);

                    -- Push the dynamic color state specifically for this text segment
                    imgui.text_colored(displayColor, toggleData.Label);

                    -- Push subsequent text elements to line up side-by-side inside the box
                    imgui.same_line();
                    imgui.text(" "); -- Tiny custom text spacing spacer
                    imgui.same_line();
                end
            end

            imgui.end();
        end
    end);

Why this fits perfectly with your migration to JSON:

- Automatic Layout Math: By invoking imgui.same_line(), you tell ImGui to pack your status strings sequentially into a clean row. If you switch from Blue Mage
  (which has 2 toggles) over to Corsair (which might have 4 or 5 active rolls/states), ImGui will automatically tile them horizontally inside the window
  boundaries without you ever having to reposition individual text boxes.

- Separation of Concerns: The code block remains identical forever. If you want to modify a font style, background color, or positional coordinate down the line,
  you don't touch this code file; you just update your layout coordinates inside the display_settings.json file.
